# เช็กลิสต์ความปลอดภัยและ PDPA — ระบบ "แจ้งก่อนจุด" (ร่างสำหรับพูดคุย)

> เอกสารนี้เป็นเช็กลิสต์ทางเทคนิคเพื่อเตรียมตัว ไม่ใช่คำปรึกษากฎหมาย
> ก่อนใช้งานจริงต้องให้เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO) / ฝ่ายกฎหมายของหน่วยงานที่เป็น "ผู้ควบคุมข้อมูล" ตรวจรับ

**สถานะปัจจุบัน:** sandbox เก็บข้อมูลในเบราว์เซอร์ของผู้ใช้เท่านั้น ไม่มีเซิร์ฟเวอร์ ไม่มีข้อมูลจริง
เช็กลิสต์ด้านล่างจึงเป็นเงื่อนไข "ก่อนย้ายเข้าใช้งานจริง"

## 1. บทบาทตาม PDPA (ต้องตกลงก่อนเก็บข้อมูลจริง)
- [ ] ผู้ควบคุมข้อมูล (Data Controller) คือใคร — โดยหลักควรเป็นกรมการปกครองหรือหน่วยงานที่รับระบบไป
- [ ] ผู้ประมวลผลข้อมูล (Processor) คือใคร — ผู้พัฒนา/ผู้โฮสต์ ต้องมีสัญญาประมวลผลข้อมูล (DPA)
- [ ] ฐานทางกฎหมายในการเก็บ: ภารกิจของรัฐ/การปฏิบัติตามกฎหมาย (ไม่ใช่ความยินยอมเป็นหลัก) — ให้ DPO ยืนยัน
- [ ] ประกาศความเป็นส่วนตัว (Privacy Notice) แสดงก่อนกรอกข้อมูล
- [ ] บันทึกรายการประมวลผล (ROPA)
- [ ] ประเมินผลกระทบ (DPIA) ถ้าข้อมูลมีพิกัด+ตัวตน+เบอร์โทร ในปริมาณมาก

## 2. ข้อมูลที่เก็บ และหลักการเก็บเท่าที่จำเป็น
| ข้อมูล | จำเป็นเพราะ | การป้องกัน |
|---|---|---|
| ชื่อ-สกุลผู้ขอ | ระบุผู้รับอนุญาต | เก็บในตาราง users |
| เลขบัตรประชาชน | ไม่เก็บค่าจริง ใช้ ThaID subject id หรือแฮช salted | ไม่เก็บดิบ |
| เบอร์โทรผู้ขอ/ผู้ประสานงาน | ติดต่อกรณีฉุกเฉิน | เข้ารหัสระดับคอลัมน์ |
| พิกัดจุดปล่อย | พิจารณาความปลอดภัยการบิน | geography; เข้าถึงตามขอบเขตอำเภอ/จังหวัด |
| ไฟล์แนบ | หลักฐานประกอบ | จำกัดชนิด/ขนาด สแกนมัลแวร์ เก็บ hash |
- [ ] ไม่เก็บข้อมูลอ่อนไหว (มาตรา 26) ไม่มีเหตุให้เก็บ
- [ ] กำหนดระยะเวลาเก็บ (ข้อเสนอเริ่มต้น: คำขอ/ใบอนุญาตตามระเบียบเอกสารราชการ, ข้อมูลติดต่อบัญชีชั่วคราวลบเมื่อหมดอายุ) — ต้องให้หน่วยงานกำหนด
- [ ] กลไกใช้สิทธิของเจ้าของข้อมูล (ขอเข้าถึง/แก้ไข/ลบ) พร้อมช่องทางติดต่อ DPO
- [ ] แผนรับมือเหตุละเมิดข้อมูล แจ้ง สคส. ภายใน 72 ชั่วโมงเมื่อมีความเสี่ยง

## 3. การยืนยันตัวตนและสิทธิ์
- [ ] ThaID ผ่านช่องทางที่ได้รับอนุมัติเท่านั้น (ต้องลงทะเบียนเป็นระบบเชื่อมต่อ — ถามกรมฯ/DGA)
- [ ] รหัสผ่านเก็บเป็น argon2id; บังคับความยาวขั้นต่ำ; จำกัดจำนวนครั้งที่ผิด (rate limit + lockout)
- [ ] เจ้าหน้าที่ต้องใช้ MFA
- [ ] RBAC ตามบทบาทและขอบเขตพื้นที่ (นายอำเภอเห็นเฉพาะอำเภอตน) บังคับที่ฝั่งเซิร์ฟเวอร์ ไม่ใช่แค่ซ่อนปุ่ม
- [ ] บัญชีชั่วคราวที่นายอำเภอออกให้ ต้องมีวันหมดอายุเสมอ (schema บังคับด้วย CHECK)
- [ ] session หมดอายุ/เพิกถอนได้; cookie แบบ Secure + HttpOnly + SameSite

## 4. OWASP Top 10 — จุดที่ระบบนี้เสี่ยงเป็นพิเศษ
- [ ] **Broken access control:** ผู้ใช้เปลี่ยน id ใน URL เพื่อดูคำขอคนอื่น (IDOR) → ตรวจสิทธิ์ทุกคำขอ (ทดสอบอัตโนมัติ)
- [ ] **Injection:** ใช้ parameterized query เท่านั้น; ตรวจพิกัดเป็นตัวเลขในช่วงประเทศไทย
- [ ] **XSS:** escape ทุกข้อความที่ผู้ใช้กรอก (เดโมนี้ใช้ฟังก์ชัน esc อยู่แล้ว) ตั้ง Content-Security-Policy
- [ ] **Upload:** whitelist ชนิดไฟล์, จำกัดขนาด, เก็บนอก web root, ตั้งชื่อใหม่
- [ ] **Logging:** audit log แบบ append-only + hash chain (มีใน schema.sql) ห้ามบันทึกรหัสผ่าน/โทเคน
- [ ] **ความถูกต้องของข้อมูลห้วงอากาศ:** ผลตรวจอัตโนมัติผิด = การตัดสินใจผิด → ระบุเวอร์ชัน/วันที่ข้อมูลทุกผลตรวจ (ตาราง auto_checks)
- [ ] **ใบอนุญาตปลอม:** QR ต้องชี้ URL ตรวจสอบสถานะสดของระบบจริง (verify_token) ไม่ใช่ลายเซ็นในภาพอย่างเดียว

## 5. โครงสร้างพื้นฐาน
- [ ] HTTPS ทั้งหมด (HSTS), TLS 1.2+
- [ ] โฮสต์และสำรองข้อมูลในประเทศไทย (ถ้านโยบายหน่วยงานกำหนด) — ถ้าอยู่ต่างประเทศต้องตรวจเงื่อนไขการส่งข้อมูลข้ามพรมแดน
- [ ] สำรองข้อมูลอัตโนมัติ + ทดสอบกู้คืนอย่างน้อยไตรมาสละครั้ง
- [ ] แยกสภาพแวดล้อม: dev / sandbox / production ใช้ฐานข้อมูลคนละชุด ห้ามนำข้อมูลจริงไป sandbox
- [ ] สแกนช่องโหว่ dependency (เช่น npm audit / pip-audit) และอัปเดตสม่ำเสมอ
- [ ] ทดสอบเจาะระบบ (pentest) **โดยได้รับหนังสืออนุญาตเป็นลายลักษณ์อักษรจากเจ้าของระบบ** ก่อนเปิดใช้จริง

## 6. ข้อตกลงที่ต้องได้จากการประชุม กปค.
1. หน่วยงานใดเป็นผู้ควบคุมข้อมูล และใครเป็น DPO ผู้ติดต่อ
2. ที่ตั้งเซิร์ฟเวอร์และมาตรฐานความปลอดภัยที่ต้องผ่าน
3. ช่องทางลงทะเบียนเชื่อม ThaID
4. ใครมีอำนาจลงนามใบอนุญาต และใบจากระบบมีผลทางกฎหมายหรือไม่
5. ระยะเวลาเก็บข้อมูลและวิธีทำลาย
6. ผู้รับผิดชอบเมื่อเกิดเหตุขัดข้องในวันจุดจริง (SLA)
